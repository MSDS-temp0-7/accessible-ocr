# 페이지 텍스트 추출 파이프라인

대상 코드: `daisy_ocr/pipeline.py`
관련 모듈: `daisy_ocr/layout/detect.py`(레이아웃 검출), `daisy_ocr/ocr/clova_engine.py`(본문 OCR)
현재 앱 연동: `daisy_ocr/server.py`의 `POST /api/v1/jobs` (PDF 렌더링, 아래 함수 호출, 결과 ZIP 생성)

> 이 문서는 큰 그림 → 세부사항 순서로 읽도록 구성했다. 1~4장만 읽어도
> "이게 뭘 하는 코드고 내가 뭘 준비해야 하는지" 감이 잡히게 했고, 실제로
> 코드를 통합할 때 필요한 세세한 내용은 5장부터 나온다. 코드와 문서가
> 어긋나면 코드(`daisy_ocr/pipeline.py`의 docstring)가 맞다 — 이 문서는
> 그걸 읽기 좋게 옮긴 것뿐이다.
>
> **내부 로직 설명 없이 함수 시그니처·예제만 빠르게 찾고 싶다면**
> [`docs/API-REFERENCE_daisy_ocr-pipeline_v1.md`](API-REFERENCE_daisy_ocr-pipeline_v1.md)를
> 대신 보면 된다 — 이 문서(왜/어떻게 설명 포함)의 축약판이다.

---

## 1. 요약 (30초 컷)

스캔한 문서 이미지 한 장을 넣으면, **사람이 읽는 순서 그대로 정렬된
텍스트 목록**을 돌려주는 코드다.

내부적으로 하는 일은 딱 세 가지다.

1. **분할** — 페이지에서 "표/그래프/수식이 있는 위치"와 "일반 글자
   위치"를 나눈다.
2. **텍스트화** — 일반 글자 부분을 OCR(광학 문자 인식)로 읽어 실제
   텍스트로 바꾼다.
3. **병합** — ①에서 찾은 표/그래프/수식 자리에 "그게 뭔지 설명한 결과"를
   끼워 넣고, ②의 텍스트와 합쳐서 원본 문서를 읽는 순서 그대로 나열한다.

**표/그래프/수식을 실제로 "무엇으로 설명할지"는 이 코드가 하지 않는다.**
그 자리를 채우는 건 다른 모델팀 몫이다. 이 코드는 "그 설명을 넣을 자리"만
찾아주고, 나중에 도착한 설명을 정확한 자리에 끼워 맞추는 역할까지만
한다.

## 2. 큰 그림 — 전체 흐름

```
                     이미지 한 장 (스캔 문서 페이지)
                             │
              ┌──────────────┴──────────────┐
              ▼                              ▼
     [분할] 표/그래프/수식        [텍스트화] 나머지 글자를
     위치 찾기                    OCR로 읽기
              │                              │
              ▼                              │
   ── 여기서부터 다른 모델팀 담당 ──            │
   "표/그래프/수식이 실제로              │
    무엇을 보여주는지" 설명 생성          │
              │                              │
              └──────────────┬──────────────┘
                             ▼
                    [병합] 중복 없이,
                  원본을 읽는 순서 그대로 합치기
                             │
                             ▼
                  최종 결과: 순서가 매겨진 텍스트 목록
```

**왼쪽 아래(텍스트화)와 오른쪽 위(분할)는 이 프로젝트 담당**이고,
**가운데(표/그래프/수식을 무엇으로 설명할지)는 다른 모델팀 담당**이다.
맨 아래 병합 단계는 다시 이 프로젝트 담당이며, 다른 팀이 만든 설명
결과를 그냥 하나의 "부품"으로 받아서 끼워 넣기만 한다 — 그 부품이 어떤
모델로 만들어졌는지는 신경 쓰지 않는다.

## 3. 처음 보면 헷갈릴 수 있는 용어

| 용어 | 쉬운 설명 |
|---|---|
| **바운딩박스(bbox)** | 이미지 안에서 "이 네모난 영역"을 가리키는 좌표 4개, `[x1, y1, x2, y2]`(왼쪽위 x,y · 오른쪽아래 x,y). 픽셀 단위. |
| **OCR** | Optical Character Recognition, 이미지 속 글자를 실제 텍스트(문자열)로 바꾸는 기술. 이 프로젝트는 CLOVA(네이버 클라우드)의 OCR API를 쓴다. |
| **레이아웃 검출** | 페이지 이미지를 보고 "여기는 표, 여기는 그림, 여기는 그냥 글자" 하는 식으로 영역과 종류를 찾아내는 AI 모델. |
| **비동기 함수 (`async`/`await`)** | 이 코드의 주요 함수들은 네트워크 호출(OCR API, AI 모델 호출)을 기다려야 해서 `async def`로 선언돼 있다. 호출할 때 `await 함수이름(...)` 형태로 써야 하고, 이런 함수는 `async def` 안에서만 부를 수 있다(파이썬 표준 문법, 이 프로젝트만의 규칙 아님). |
| **데이터 클래스(dataclass)** | 여러 값을 이름 붙여 하나로 묶은 파이썬 객체. `상자.text`, `상자.bbox`처럼 점(`.`)으로 값을 꺼낸다 — 딕셔너리의 `상자["text"]`와 비슷하지만 필드 이름이 미리 정해져 있어 오타를 IDE가 바로 잡아준다. |
| **겹침 비율(IoU)** | 두 바운딩박스가 서로 얼마나 겹치는지 0~1 사이 숫자로 나타낸 것. `(겹치는 부분의 넓이) ÷ (두 박스를 합친 넓이)`. 완전히 같은 자리면 1, 전혀 안 겹치면 0. |
| **포함 비율** | "작은 박스가 큰 박스 안에 얼마나 들어가 있는지"를 보는 값. `(겹치는 부분의 넓이) ÷ (더 작은 쪽 박스의 넓이)`. 크기 차이가 큰 두 박스가 사실 같은 대상을 가리킬 때 겹침 비율(IoU)만으로는 못 잡는 경우를 잡으려고 같이 쓴다(계산 절차는 §10.1, 왜 필요한지는 §11.3에서 실제 사례로 설명). |

## 4. 담당 범위 — 무엇을 하고, 무엇을 안 하는가

| 함수 | 우리 담당 | 하는 일 | 다른 팀 모델(OpenAI 등)을 부르는가 |
|---|---|---|---|
| `prepare_page()` | ✅ | ① 분할 + ② 텍스트화 | 아니오 |
| `merge_page()` | ✅ | ③ 병합 | 아니오 |
| `transcribe_regions()` | ❌ (지금은 임시로 우리가 채워둔 것) | 표/그래프/수식을 실제로 설명 | 예 — OpenAI. **다른 모델팀 결과물로 통째로 바뀔 부분** |
| `process_page()` | ❌ (편의용) | 위 셋을 한 번에 이어붙인 함수. 데모 웹앱 전용 | 예(내부에서 `transcribe_regions()`를 부름) |

핵심: **`prepare_page()`와 `merge_page()`는 OpenAI를 전혀 모른다.**
표/그래프/수식을 무엇으로 설명하든(OpenAI든, 다른 모델팀의 자체 모델이든)
그 결과를 정해진 형태(§8의 `TranscribedRegion`)로만 `merge_page()`에
넘기면 똑같이 동작한다. `transcribe_regions()`와 `process_page()`는
"지금 당장 결과물을 보여주려고 OpenAI로 채워둔 자리채우기용" 코드다.

## 5. 준비물 — 환경변수

호출 전에 `.env` 파일에 아래 값을 넣고 `load_dotenv()`를 한 번
실행해둬야 한다(애플리케이션 시작 시 한 번이면 충분).

| 변수 | 언제 필요한가 | 용도 |
|---|---|---|
| `CLOVA_OCR_SECRET` | 항상 | CLOVA OCR 인증 키(Secret Key). 기존 `CLOVA_GATEWAY` 이름도 호환용으로 읽지만 새 앱 설정에는 사용하지 않는다. |
| `CLOVA_OCR_INVOKE_URL` | 항상 | CLOVA OCR을 호출할 주소. `https://xxxx.apigw.ntruss.com/...` 형태여야 한다 — `ncloud.com`으로 끝나는 내부용 주소가 아님(과거에 잘못된 주소를 넣어 연결이 안 됐던 적이 있으니 주의) |
| `OPENAI_API_KEY` | `transcribe_regions()`나 `process_page()`를 쓸 때만 | 지금 참고 구현이 표/그래프/수식 설명에 쓰는 OpenAI 호출용. 다른 모델팀 결과물로 완전히 바꾸면 이 키 자체가 필요 없어진다 |

`prepare_page()`와 `merge_page()`만 쓴다면 `OPENAI_API_KEY`는 없어도
된다 — 이 둘은 OpenAI를 전혀 부르지 않는다(§4 참고).

## 6. 빠른 시작

```python
import asyncio
from dotenv import load_dotenv
from PIL import Image
from daisy_ocr.pipeline import prepare_page, merge_page

load_dotenv()  # .env에서 API 키를 읽어온다 (§5 참고)

async def main():
    image = Image.open("page.jpg").convert("RGB")

    # ① + ② 우리 담당: 분할 + 텍스트화
    prepared = await prepare_page(image)

    # (다른 모델팀 자리) 지금은 아무 설명도 안 만들고 빈 채로 병합해본다
    elements = merge_page(prepared.ocr_blocks, prepared.non_text_regions, transcribed=[])

    for el in elements:
        print(el.text)

asyncio.run(main())
```

표/그래프/수식 설명까지 다른 팀 모델로 채워 넣는 실전 형태는 §8에 있다.

## 7. 함수 상세 — `prepare_page()`

### 7.1 입력

```python
async def prepare_page(
    image: PIL.Image.Image,
    *,
    layout_model: str = "doclaynet",
    conf: float | None = None,
    imgsz: int | None = None,
) -> PreparedPage
```

| 파라미터 | 타입 | 기본값 | 설명 |
|---|---|---|---|
| `image` | `PIL.Image.Image` | (필수) | RGB로 변환된 페이지 이미지. 호출 전 `.convert("RGB")` 해둘 것. |
| `layout_model` | `str` | `"doclaynet"` | 레이아웃 검출에 쓸 모델 이름. `daisy_ocr.layout.detect.MODELS`에 등록된 것 중 선택. |
| `conf` | `float \| None` | `None` | 레이아웃 검출의 확신도 문턱값(이 값보다 자신 없는 검출은 버림). `None`이면 등록된 기본값(현재 `0.3`, §12.1 참고) 사용. |
| `imgsz` | `int \| None` | `None` | 레이아웃 검출이 이미지를 몇 픽셀로 리사이즈해서 볼지. `None`이면 등록된 기본값(`960`) 사용. |

### 7.2 출력 — `PreparedPage`

```python
@dataclass
class PreparedPage:
    ocr_blocks: list[TextBlock]           # OCR로 읽은 텍스트 조각들(문서 전체)
    regions: list[LayoutRegion]           # 레이아웃 검출 원본 결과(중복 제거 전)
    non_text_regions: list[LayoutRegion]  # 표/그래프/수식/악보 위치만, 중복 제거 완료
    layout_model: str
    conf: float
    imgsz: int
    ocr_elapsed_ms: float     # OCR에 걸린 시간(ms)
    detect_elapsed_ms: float  # 레이아웃 검출에 걸린 시간(ms)
```

다음 단계(다른 모델팀)에 넘길 건 `non_text_regions` 하나뿐이다. 이 안의
`LayoutRegion` 하나하나는 `label`(레이아웃 모델이 붙인 원래 이름, 예:
`"Table"`)·`bbox`·`confidence` 세 값을 가진다.

`ocr_blocks`는 `merge_page()`에 그대로 넘길 텍스트 조각 목록이다 —
개별적으로 다룰 일은 거의 없다.

## 8. 다른 모델팀이 채울 자리 — `TranscribedRegion` 계약

표/그래프/수식을 "무엇으로 설명할지" 만드는 모델이 무엇이든, `merge_page()`에
넘길 때는 이 형태 하나로만 맞추면 된다:

```python
@dataclass(frozen=True)
class TranscribedRegion:
    type: str          # "table" | "formula" | "graph" | "music" | "unknown"
    label: str          # 원래 레이아웃 라벨(예: "Table") — 자유롭게 채워도 됨
    bbox: tuple[float, float, float, float]  # non_text_regions의 그 영역과 같은 좌표
    confidence: float   # 이 결과에 대한 확신도(0~1)
    text: str | None    # 설명/변환 결과. 실패했으면 None
    error: str | None = None  # 실패 사유. 성공이면 None
```

주의할 점 하나: `bbox`가 `prepared.non_text_regions`에 있던 영역의 좌표와
**같아야** `merge_page()`가 "이게 어느 자리 설명인지" 올바르게 찾는다.
보통은 `non_text_regions`를 순회하면서 각 영역의 `bbox`를 그대로 복사해
쓰면 된다.

### 8.1 실전 예시 — 다른 팀 모델을 직접 연결하는 코드

```python
from daisy_ocr.pipeline import prepare_page, merge_page, TranscribedRegion

prepared = await prepare_page(image)

transcribed = [
    TranscribedRegion(
        type="table",                     # 이 영역이 표라고 다른 팀 모델이 판단
        label=region.label,
        bbox=region.bbox,                 # 반드시 같은 좌표를 그대로 씀
        confidence=region.confidence,
        text=다른팀_모델_호출(image, region.bbox),  # 실제 모델 추론
        error=None,
    )
    for region in prepared.non_text_regions
]

elements = merge_page(prepared.ocr_blocks, prepared.non_text_regions, transcribed)
```

## 9. 함수 상세 — `merge_page()`

### 9.1 입력·출력

```python
def merge_page(
    ocr_blocks: list[TextBlock],           # prepared.ocr_blocks 그대로
    non_text_regions: list[LayoutRegion],  # prepared.non_text_regions 그대로
    transcribed: list[TranscribedRegion],  # §8의 결과(다른 팀이 만든 것)
) -> list[PageElement]
```

`await` 필요 없는 일반 함수다(네트워크 호출이 없어서). `transcribed`를
빈 리스트로 주면 표/그래프/수식 설명 없이 OCR 결과만 순서대로 나온다.

### 9.2 결과 하나하나 — `PageElement`

```python
@dataclass(frozen=True)
class PageElement:
    kind: str                    # "ocr"(글자) | "ai"(표/그래프/수식 설명)
    type: str                    # ocr는 항상 "text". ai는 table|formula|graph|music|unknown
    text: str                    # 실제 내용
    bbox: tuple[float,float,float,float]  # 원본 이미지에서의 위치
    confidence: float | None     # ocr만 값 있음(OCR 인식 확신도)
    label: str | None            # ai만 값 있음(원래 레이아웃 라벨)
    error: str | None            # ai 설명이 실패했을 때만 값 있음
```

이 리스트를 앞에서부터 순서대로 읽으면 원본 문서를 사람이 읽는 순서와
같다(정렬 절차는 §10.3, 정렬 방식을 이렇게 정한 이유는 §11.5). 사용 예:

```python
for el in elements:
    if el.kind == "ocr":
        print(el.text, end=" ")
    else:
        print(f"\n[{el.type}] {el.text}\n")
```

## 10. 핵심 알고리즘 상세 — 실제로 어떻게 계산하나

§9까지가 "무엇을 넣으면 무엇이 나오는가"였다면, 이 장은 `merge_page()`와
`prepare_page()` 안에서 실제로 어떤 단계를 거치는지를 숫자와 함께
따라가 본다. 왜 이런 방식을 택했는지는 §11에서 다룬다 — 이 장은 "왜"가
아니라 "어떻게"에만 집중한다.

### 10.1 표/그래프/수식 중복 제거 — `dedupe_regions()`

**입력**: 레이아웃 모델이 찾은 비텍스트 영역 목록(같은 표/수식을 두 번
이상 찾았을 수 있음). **출력**: 중복이 정리된 영역 목록.

**단계**:

1. 영역들을 확신도(confidence) 높은 순으로 줄 세운다.
2. "채택 목록"을 빈 상태로 시작한다.
3. 확신도 순서대로 영역을 하나씩 검사한다. 이미 채택 목록에 있는 것 중
   **같은 라벨(예: 둘 다 `"Formula"`)인 것들과만** 비교해서:
   - 겹침 비율(IoU) **또는** 포함 비율이 문턱값(각각 0.5, 0.8)을
     넘으면 → 이미 채택된 것과 같은 대상이라고 보고 **버린다**.
   - 둘 다 안 넘으면 → 새로운 대상이라고 보고 채택 목록에 **추가한다**.
4. 채택 목록을 돌려준다.

**손으로 따라가는 예시** (실제로 관측된 수식 검출 결과):

| 박스 | 확신도 | 크기 |
|---|---|---|
| A | 0.39 | 큼(수식 두 줄 전체를 담음) |
| B | 0.36 | 작음(A 안에 완전히 포함된, 마지막 한 줄만) |

확신도 순서는 A → B. A는 채택 목록이 비어 있으니 그냥 채택.
B를 검사할 차례: B는 A 안에 거의 통째로 들어가 있으므로 포함 비율이
**1.0**으로 나온다(B 넓이 전부가 A와 겹침) → 문턱값 0.8을 넘으므로
중복 판정 → **B는 버려진다**. 최종적으로 A 하나만 남는다.

만약 겹침 비율(IoU)만 썼다면 어땠을까? A가 B보다 훨씬 커서 IoU는
`(겹치는 넓이) ÷ (A와 B를 합친 넓이)`로 계산되고, 분모가 A의 큰 넓이에
끌려가 낮은 값(약 0.2)이 나온다 — 문턱값 0.5를 못 넘어서 **중복으로
못 잡았을 것**이다. 포함 비율을 같이 보는 이유가 이것이다.

### 10.2 표/그래프/수식 자리와 겹치는 OCR 글자 제거 — `is_covered_by_any_region()`

**입력**: OCR 글자 조각 하나의 위치(bbox), 비텍스트 영역 목록.
**출력**: 이 글자 조각을 "이미 다른 곳(비텍스트 설명)이 대표하고
있으니 빼도 되는가"에 대한 예/아니오.

**단계** (OCR 조각 하나마다 반복):

1. 이 조각 자신의 넓이를 구한다.
2. 비텍스트 영역을 하나씩 보면서, 조각과 그 영역이 겹치는 부분(교집합)의
   넓이를 구한다.
3. `교집합 넓이 ÷ 조각 자신의 넓이`가 0.3(30%)을 넘는 영역이 **하나라도**
   있으면 → "빼도 됨"(True)이라고 즉시 답한다.
4. 모든 영역을 다 봐도 30%를 넘는 게 없으면 → "그대로 둠"(False).

이 판정을 `prepare_page()`가 읽은 모든 OCR 조각에 대해 반복해서, "빼도
됨"으로 나온 조각들만 결과에서 제외한다.

**실측 예시**: 수식이 많은 실제 문서 한 장으로 검증했을 때, OCR이 읽은
글자 조각 236개 중 94개가 비텍스트 영역과 30% 이상 겹쳐서 제외 대상으로
판정됐다. 실제로 그 94개를 빼고 남은 142개만 최종 결과에 포함시켰더니,
표/수식 안의 글자가 원문 그대로 중복 표시되던 문제가 사라졌다(빠뜨리고
남겨진 것도, 잘못 지워진 것도 0개 — 좌표를 다시 계산해서 확인함).

### 10.3 읽기 순서 정렬 — `order_by_reading_flow()`

**입력**: 최종 결과에 들어갈 항목들(OCR 조각 + 비텍스트 설명), 아직
순서 없음. **출력**: 사람이 문서를 읽는 순서대로 정렬된 목록.

**단계**:

1. 항목을 두 그룹으로 나눈다 — OCR 글자 조각과 비텍스트(표/그래프/수식)
   설명.
2. **OCR 조각들만** 상단 y좌표 기준으로 오름차순 정렬한다.
3. 정렬된 순서대로 조각을 하나씩 훑으며 "줄" 목록에 배정한다:
   - 기존 줄 중에 지금 조각과 **세로 구간이 40% 이상 겹치는** 줄이
     있으면 그 줄에 편입시킨다. 이때 **그 줄의 기준 범위는 절대
     넓히지 않는다**(그 줄을 처음 만든 조각의 세로 범위 그대로 유지).
   - 겹치는 줄이 없으면, 이 조각을 기준으로 새 줄을 만든다.
4. 비텍스트 설명 항목은 (2)~(3)을 거치지 않고, **각자 혼자만의 새 줄로**
   그대로 추가한다 — 다른 항목과 절대 묶이지 않는다.
5. 모든 줄을 (줄을 만든 첫 조각의) 상단 y좌표 기준으로 정렬한다.
6. 각 줄 안에서는 항목들을 왼쪽 x좌표 기준으로 정렬한다.
7. 줄 순서대로, 각 줄 안에서는 정해진 순서대로 이어 붙여 최종 목록을
   만든다.

**손으로 따라가는 예시** (실제 문서 하단의 "사업계획서 / 토지등기부등본"
2단 목록):

| 항목 | 상단 y | 왼쪽 x |
|---|---|---|
| 토지등기부등본 | 2822 | 1433 (오른쪽) |
| 사업계획서 | 2826 | 667 (왼쪽) |
| 토지사용 | 2921 | 1433 (오른쪽) |
| 승락서 | 2921 | 1662 (오른쪽) |
| 토지대장등본 | 2929 | 667 (왼쪽) |

y좌표 오름차순으로 보면 "토지등기부등본"(2822)이 "사업계획서"(2826)보다
먼저 나오지만, 둘의 세로 구간이 크게 겹쳐서(40% 훨씬 이상) **같은
줄로 묶인다**. 그 줄 안에서 x좌표로 다시 정렬하면 "사업계획서"(x=667,
왼쪽)가 "토지등기부등본"(x=1433, 오른쪽)보다 앞에 온다 — 사람이 왼쪽부터
읽는 순서와 일치한다. 다음 줄("토지사용/승락서/토지대장등본")도 같은
방식으로 묶여 "토지대장등본 → 토지사용 → 승락서" 순으로 나온다.

이 예시에서 (3)단계의 "줄 범위를 넓히지 않는다"가 왜 중요한지도 보인다
— 만약 범위를 계속 넓혔다면, 위 표의 5개 항목이 서로 y구간이 살짝씩
겹치면서 사슬처럼 전부 하나의 줄로 뭉쳐(§11.5에서 실제로 이 버그가
발생했던 경위 설명), 왼쪽 세 줄이 오른쪽 항목들보다 먼저 나와버리는
잘못된 순서가 됐을 것이다.

## 11. 왜 이렇게 만들었나 — 설계 결정과 근거

이 장은 "그냥 그렇게 하면 되는 거 아냐?"라는 질문에 대한 답이다. 전부
실제로 문제를 겪고 고친 기록이다.

### 11.1 왜 표/그래프/수식 영역만 찾고, 글자는 레이아웃과 상관없이 통째로 읽나

처음엔 "레이아웃 모델이 찾은 박스 안쪽만 잘라서 OCR"했다. 문제는
레이아웃 모델이 모든 글자 영역에 박스를 완벽하게 그려주지 않는다는
것이다 — 박스를 놓친 부분은 글자가 통째로 사라졌다. 그래서 **글자는
레이아웃 검출과 완전히 별개로 페이지 전체를 OCR로 훑고, 레이아웃 모델은
"글자가 아닌" 부분(표/그래프/수식)만 찾아 그 자리만 표시**하도록 바꿨다.

### 11.2 왜 OCR 엔진으로 CLOVA를 골랐나

| 후보 | 결과 |
|---|---|
| PaddleOCR | Windows에서 실행 자체가 안 되는 버그 발견(미해결) |
| EasyOCR | 한국어 인식 품질이 눈으로 봐도 낮음 |
| RapidOCR | 실측: 정답 단어 중 79.0%만 맞게 찾음 |
| **CLOVA OCR (채택)** | 실측: 95.2% |
| OpenAI 비전 모델로 글자 읽기 | 정확도는 94.9%로 CLOVA와 비슷했지만, 없는 내용을 그럴듯하게 지어내는 위험이 있고(글자를 "인식"하는 게 아니라 "보고 답하는" 방식이라서) 속도도 3배 느려 제외 |

### 11.3 왜 표/그래프/수식 위치를 "중복 제거"해야 하나

레이아웃 모델이 확신도 문턱값을 낮게 잡을수록(더 많이 찾으려 할수록)
**같은 자리에 거의 겹치는 박스가 여러 개** 잡힌다 — 실측으로 수식 하나에
박스가 최대 20개까지 나온 적이 있다. 이걸 그대로 다른 모델팀에 넘기면
같은 표/수식을 여러 번 설명하게 된다.

단순히 "겹침 비율(IoU)이 높으면 하나만 남기기"만으로는 부족했다 — 크기
차이가 큰 두 박스(작은 박스가 큰 박스 안에 완전히 들어있는 경우)는
겹침 비율이 낮게 나온다(분모가 큰 박스 넓이라서). 그래서 **겹침 비율과
포함 비율 중 하나라도 문턱값을 넘으면 중복으로 보고 확신도가 더 높은
것만 남기는** 방식을 쓴다.

### 11.4 왜 OCR 결과에서 표/그래프/수식 자리의 글자를 따로 빼야 하나

OCR은 페이지 전체를 훑기 때문에(§11.1), 표/그래프/수식 안에 있는 글자도
그대로 읽어온다. 그 자리를 다른 모델팀이 이미 설명했다면, 같은 내용이
날것 그대로(가공 안 된 원문 그대로) 한 번 더 나와 중복된다.

처음엔 "OCR 조각의 중심점이 표/그래프/수식 영역 안에 있는가"로 판단했는데,
OCR이 주변 문장과 그 안의 글자를 하나로 묶어버리면 중심점이 영역 밖으로
빠지는 경우가 실제로 있었다(그래서 중복이 안 걸러짐). 그래서 **"OCR
조각 자신의 넓이 중 30% 이상이 표/그래프/수식 영역과 겹치는가"**로
기준을 바꿨다.

**이 필터는 레이아웃 모델이 실제로 박스를 그린 경우에만 동작한다.**
문장 속에 짧게 섞인 수식(예: "F1=xy2, F2=3")처럼 레이아웃 모델이 애초에
박스를 그리지 않는 경우는 걸러낼 대상 자체가 없다 — 이건 지금 이
파이프라인이 풀지 못한 유일한 한계다(§13 참고).

### 11.5 왜 단순히 위에서 아래로만 정렬하면 안 되나

문서 양식엔 "이름 / 연락처 / 주소"처럼 한 줄에 여러 항목이 나란히
있는 경우가 많다. 이럴 때 각 항목의 y좌표(세로 위치)는 OCR이 인식할
때마다 몇 픽셀씩 다르게 나올 수 있어서, 단순히 y좌표로만 정렬하면
같은 줄인데 순서가 뒤섞인다.

그래서 **"세로 구간이 40% 이상 겹치면 같은 줄"로 묶고, 같은 줄 안에서는
가로(x) 순서로, 줄과 줄 사이는 세로(y) 순서로** 정렬한다. 이 방식을
만들며 실제로 두 가지 버그를 겪었다:

1. **표/그래프 설명은 "한 줄"이 아니라 문단 하나를 통째로 차지한다.**
   이런 항목까지 같은 줄 묶기 로직에 넣으면, 세로로 긴 항목 하나가
   섞이는 순간 그 줄의 범위가 확 넓어져서 그 아래 있는 상관없는 글자
   줄들까지 전부 같은 줄로 잘못 묶여버렸다. 그래서 표/그래프 항목은
   애초에 줄 묶기 대상에서 뺐다.
2. **글자 조각끼리 묶을 때도, 줄의 기준 범위를 계속 넓히면 안 된다.**
   촘촘히 붙어 있는 여러 줄을 순서대로 검사하면서 "묶일 때마다 범위를
   넓히는" 방식으로 짜면, 사슬처럼 계속 이어 붙어 관계없는 줄까지
   하나로 뭉쳐버리는 버그가 실제로 발생했다(문서 하단 항목 목록에서
   확인). 그래서 줄의 기준 범위는 그 줄을 처음 만든 항목의 것으로
   고정해 둔다.

## 12. 실측 근거

이 문서의 설계 결정은 전부 재현·측정한 값에 근거한다. 값이 바뀌면 이
표도 같이 갱신할 것.

| 항목 | 측정값 | 근거 |
|---|---|---|
| CLOVA 어절 인식 정확도 | 95.2% (AI Hub 문서 10장) | RapidOCR(79.0%)·OpenAI 비전(94.9%)과 비교 |
| 확신도 문턱값 0.02 → 0.3 전환 시, 표/수식/그림 재현율 | 표 0.913→0.913, 수식 1.0→0.971, 그림 0.951→0.934 | DocLayNet 문서 100장, 포함 비율 기반 지표(§12.1 참고) |
| 같은 전환 시 페이지당 검출 영역 수 | 18.3개 → 13.2개 (28% 감소) | 같은 100장 |
| 확신도 0.02에서 수식 1개당 최대 중복 검출 박스 수 | 20개 | 실제 논문 문서 1장 실측 |
| 중복 글자 제거 필터의 정확도 | 94개 중 94개(100%) 정확히 제거, 잘못 지운 것 0개 | 좌표 기준 재계산으로 검증 |

### 12.1 확신도 기본값을 0.02에서 0.3으로 바꾼 이유

예전엔 확신도 문턱값 0.02가 0.3보다 훨씬 낫다("0.959 대 0.935")고
측정됐었다. 이건 **입도(글자 뭉치는 단위)가 다르면 왜곡되는 지표**로 잰
값이었다 — 더 정확한 방식(포함 비율 기반, 위 표에서 쓴 것)으로 다시
재보니 그 정도로 크게 차이 나지 않았다. 오히려 확신도를 낮게 잡을수록
중복 검출이 늘어(§11.3) 다른 모델팀 호출이 낭비되는 비용이 있었다. 그래서
기본값을 **0.3**으로 확정했다(`daisy_ocr/layout/detect.py`의
`MODELS["doclaynet"].conf`).

## 13. 알려진 한계

1. **문장 속에 섞인 짧은 수식은 못 걸러낸다.** (예: "F1=xy2, F2=3")
   레이아웃 모델이 이런 건 애초에 별도 박스로 잡지 않아서, OCR이 기호가
   깨진 채로 그대로 반환한다. "글자 패턴만 보고 이런 걸 걸러내자"는
   시도(로컬 AI 모델, OpenAI 둘 다)도 해봤는데, 전화번호·날짜·금액처럼
   숫자·기호가 섞인 정상적인 글자까지 대량으로 잘못 지워버려서(실측:
   정상 문서 본문의 45%가 잘못 삭제됨) 위험하다고 판단해 적용하지
   않았다. 현재 미해결.
2. **표 구조를 실제로 검증하지 않는다.** 지금 참고 구현은 "표를
   마크다운으로 옮겨 적어줘"라고 AI에 요청만 할 뿐, 셀 병합이나 숫자가
   맞는지 확인하는 로직은 없다. 정식 표 처리 파이프라인의 임시
   대역일 뿐이다.
3. **로컬 AI 모델로 후처리를 시도했지만 채택하지 않았다.** 중복 문장
   정리, 인라인 수식 판별 둘 다 로컬 AI 모델(qwen3.5)로 시도했으나,
   "깊이 생각하게" 설정하면 정확하긴 한데 페이지 하나에 8~16분이 걸렸고
   (항목이 많을수록 더 오래 걸림), "빨리 답하게" 설정하면 판단 자체를
   포기해버렸다(즉시 빈 답변). 그래서 실전에는 넣지 않았다.
